Design Note: MayaCardio Biosignal Pipeline

"Never Lose a Heartbeat" · Software Systems Engineering Assessment · October 2026

1. Architecture

The on-device pipeline is structured into decoupled, single-responsibility components operating over local inter-thread queues and an ACID SQLite backing store:

biosignal-mock (TCP 7100) ──> [Reader × 2] ──> [Loss Recorder] ──> [Durable Store: SQLite WAL] ──> [Offline Processor]
                                                     │                   │                                 │
                                                     └───────────────────┼──> [Uploader] ──HTTPS──> Cloud API
                                                                         └──> [Mode Controller] (Health Probes)

Durable Store (SQLite WAL + synchronous=FULL): SQLite in Write-Ahead Logging mode provides true ACID crash-safety and process-crash resilience. A composite primary key (session_id, sensor, idx) guarantees that sample re-reads from the mock or re-submissions from network interruptions are idempotent via INSERT OR IGNORE. Queries for export, window boundaries, and catch-up ack cursors are executed as standard B-tree queries with zero custom serialization overhead.

Monotonic Index-Based Ordering: Wall clocks fluctuate due to NTP corrections, daylight savings, or power cuts. All sample ordering, gap detection, and 400-sample window segmentations rely solely on integer sample indices. Monotonic timers (time.monotonic()) are restricted strictly to relative timeouts (reconnection backoffs, health-probe intervals).

Component Workflow:

  • Readers (1 per sensor): Stream newline-delimited JSON chunks from TCP 7100. Extract data substring directly to verify zlib CRC-32 against the reply header. Detect gaps (first_index > expected_next) and log loss records immediately.
  • Commit Policy: Batches of up to 400 samples (1 s) per sensor are committed atomically with cursor checkpoints inside single SQLite transactions.
  • Mode Controller: Probes Cloud /v1/health every 2 s. Switches to offline after 2 consecutive failures (≤4 s, well within 10 s limit); returns to online after 2 consecutive successes and uploader handshake.
  • Uploader & Catch-up: In online mode, POSTs 1-second sample batches to /v1/samples. Advances cloud_ack only upon HTTP 200. On network restoration, switches to 60-second bulk catch-up batches until backlog reaches zero.
  • Processing Engine: Shared processing.py module calculates 1-second window stats, peak candidate gating (100-sample gap), and heart rate (60 × 400 / mean peak gap) identically on cloud and device.

2. What is Guaranteed

GuaranteeUnderlying Architectural Mechanism
Zero Silent LossEvery missing sample is caught via gap detection, mock-reported loss, CRC failure, or disk-full handler, and durably written to losses.
Exactly-Once StorageUnique constraint on (session_id, sensor, idx) with INSERT OR IGNORE discards duplicate arrivals cleanly.
No Switch Loss / DupReaders collect uninterrupted during network mode changes; uploaders resume safely from cloud_ack.
Idempotent Cloud IngestionCloud API shares the identical composite primary key schema; resending unacknowledged batches cannot create duplicates.
Processing EquivalenceDevice offline processor and Cloud API import the exact same pure-Python processing.py and pass reference parity checks.

3. What is NOT Guaranteed

  • Pre-read Mock Drops: Samples dropped by the mock's internal 10-second ring buffer before pipeline connection are unrecoverable; these are logged as buffer_overflow based on mock replies.
  • Lying SD Card Hardware: If an underlying SD card / disk controller acknowledges flush/fsync without physical commit, sudden power pull during dirty block writes may cause data loss beyond stated bounds.
  • Unbounded Cloud Availability: Free-tier cloud instances lack strict enterprise SLAs; device gracefully falls back to offline storage and processing during prolonged cloud downtime.
  • Online Deadline during Packet Degradation: If the network maintains high latency without dropping packets, health probes may pass while transfers lag; a 3-second grace period prevents processing starvation.

4. Maximum Data Loss on Power Cut

Stated Design Bound (Assumption A8): ≤ 400 samples per sensor (≤ 1.0 second of data).

Technical Rationale: The pipeline accumulates samples in memory and commits to the durable SQLite WAL store every 400 samples (1 second of data) or on a 1.0-second timer, whichever occurs first, using PRAGMA synchronous = FULL. Upon an abrupt power severance, at most the uncommitted in-memory batch is unwritten. On reboot, integrity checks run, committed cursors load, and unread ranges are detected as loss gaps.

Measured in Software Simulation: In simulated power cuts (process termination via kill -9 without sync during active ingestion), uncommitted sample loss was bounded at 0 to 384 samples per sensor. In the run recorded in evidence/02_power_cut, clean SQLite WAL recovery succeeded with 0 corrupted records.

6. Assumptions Register & Implementation Notes

#AssumptionOperational Application
A1Sample AvailabilityA sample is available if stored in the processing location's database and not indexed in a loss record.
A2Magnitude CalculationMean magnitude of √(ch1² + ch2²) returns null when zero sensor-2 samples exist in the window.
A3Heart-Rate Missing CheckMissing-sample validation for heart-rate gating applies specifically to sensor-1 (ECG) data.
A4Peak Collision PolicyA peak candidate failing the 100-sample gap is dropped; the earlier peak retains precedence.
A5Decimal RoundingAll floating-point results round to 1 decimal place using half-up arithmetic consistently.
A6Dual Mode ResultsBoth offline and online result lines are stored and outputted; the mode key disambiguates them.
A7Window Grace PeriodOnline processor waits at most 3.0 s for missing window data before emitting a partial window.
A8Power Cut BoundWorst-case power-cut data loss bound is 400 samples/sensor (1 second batch commit interval).
A9Session UnitExport and processing sessions are scoped by the mock's 32-bit hexadecimal session_id.
