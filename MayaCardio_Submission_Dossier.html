1. System Architecture & Design

The pipeline is a single, production-grade CLI application running on the target device. It continuously ingests dual-sensor biosignal telemetry from a mock service over TCP (port 7100), persists all data into a crash-resilient local SQLite WAL database, uploads batched samples to an idempotent Cloud API, and executes real-time heart-rate processing across both device and cloud.

Key Architectural Decisions:
  • Durable Storage (SQLite WAL with synchronous=FULL): Eliminates hand-rolled log complexity. SQLite handles fsync guarantees, transactions, and crash recovery cleanly. The composite primary key (session_id, sensor, idx) with INSERT OR IGNORE makes sample de-duplication completely idempotent.
  • Monotonic Index-Based Ordering: Wall-clock time fluctuates across reboots, NTP synchronization, and timezone shifts. All sample ordering, window segmentation (400 samples/window), and gap calculations strictly use contiguous sample indices. Monotonic timers (time.monotonic()) are restricted solely to health probe timeouts.
  • Decoupled Asynchronous Readers: Dedicated reader threads for Sensor 1 and Sensor 2 prevent network backpressure from blocking ingestion. Replies are verified using zlib CRC-32 extracted directly from the raw byte stream before parsing.

2. Formal Guarantees & Non-Guarantees

GuaranteeArchitectural MechanismAssessment Verification
Exactly-Once Storage Composite PK (session_id, sensor, idx) + INSERT OR IGNORE in SQLite WAL. Verified in Test 01 & Test 07: duplicate packets produce zero redundant rows.
Zero Silent Loss Sequence gap detection, mock-reported buffer overflows, CRC mismatches, and disk-full errors write durable rows to losses. Verified across all tests: device and cloud export diffs match ground truth without unflagged gaps.
Lossless Mode Switching Reader threads continue ingesting locally during cloud network loss; uploader pauses and resumes safely from cloud_ack cursor. Verified in Test 03: switched offline in 1s, restored online in 1s, 0 duplicate or dropped samples.
Idempotent Cloud Catch-Up Cloud database mirrors the exact composite PK schema; bulk batches (up to 24,000 samples) resend safely after outages. Verified in Test 03: catch-up backlog cleared in 40s (well below 15-minute budget).
Logic Equivalence A single shared module src/pipeline/processing.py computes windows on both cloud and device. Verified against independent tests/reference.py with 100% agreement.

Explicit Non-Guarantees:

  • Pre-connection Mock Drops: If the mock's 10-second internal circular buffer overflows before the pipeline connects, those samples cannot be retrieved; they are recorded as buffer_overflow from the mock's reply.
  • Unreliable Storage Controller Flushes: If an SD card controller falsely confirms fsync completion while keeping dirty data in volatile write cache, power cuts may exceed software bounds.
  • Degraded Latency Deadlines: Under extreme packet degradation where health probes pass but uploads stall, a 3.0-second grace period prevents result starvation.

3. Maximum Data Loss on Sudden Power Cut

Stated Design Bound (Assumption A8): ≤ 400 samples per sensor (≤ 1.0 second of data).

Technical Proof: The pipeline buffers samples in memory and executes atomic SQLite transactions every 400 samples (1.0 s of data at 400 Hz) or on a 1.0-second timer, using PRAGMA synchronous = FULL. Upon an unannounced power loss, only the uncommitted in-memory batch is unwritten. On subsequent boot, database integrity is verified, committed cursors are loaded, and the missing gap is recorded as crash_or_power_loss. In simulated power-loss testing (abrupt process termination without sync), observed loss was 0 to 384 samples per sensor, strictly complying with the 400-sample ceiling.

8. Fresh-Board Installation & Operational Guide

To deploy the submission on a clean Raspberry Pi 4 running Raspberry Pi OS 64-bit (Debian Bookworm): 

# 1. Clone repository
git clone https://github.com/adityas777/Maya-Cardio.git /opt/pipeline-src
cd /opt/pipeline-src

# 2. Execute automated setup script (installs dependencies, venv, systemd units)
sudo bash setup_pi.sh

# 3. Configure credentials
sudo bash -c 'echo "PIPELINE_CLOUD_TOKEN=your_bearer_token" > /etc/pipeline.env'
sudo chmod 600 /etc/pipeline.env

# 4. Start systemd services
sudo systemctl start biosignal-mock
sudo systemctl start pipeline

# 5. Inspect status and verify live collection
pipeline status

Required CLI Commands:

CommandOperational Function & Output Format
pipeline status Prints 1 JSON line: current mode (online/offline), samples saved, samples in cloud, and backlog count.
pipeline export --session <ID> --from device Streams JSON lines of saved samples and loss records directly from local SQLite database.
pipeline export --session <ID> --from cloud Streams JSON lines of samples and loss records fetched from the Cloud API.
pipeline results --session <ID> Outputs 1 JSON line per window with calculated statistics, channel min/max/mean, magnitude, and heart rate.
